### Новые замечания и регрессии

#### A37. Для новых пользователей отсутствует доступный сценарий восстановления

- **Приоритет / статус:** средний; подтверждено исходниками, defaults дампа/тестовой схемы и проверкой с моделью БД в памяти. Наличие внешнего процесса настройки восстановления неизвестно.
- **Место:** `backend/models/authModel.js:17`, `:33`, `:40`; `backend/controllers/authController.js:35`; `frontend/src/pages/users.tsx:105`; схема users в itk_old.sql.
- **Проблема и последствия:** createUser не записывает question/answer; по представленной схеме они остаются NULL. recPass/recAns правильно отказывают без настроенных данных. Собственных маршрутов/форм настройки question/answer или отдельного сброса менеджером нет. Созданный через UI сотрудник после потери пароля не сможет пройти имеющееся восстановление. Это пробел полного сценария; возвращать приём пустого ответа нельзя.
- **Исправление:** вместе с усилением A02 определить надёжный канал восстановления и безопасное первичное подключение новых пользователей либо явно согласованный административный reset с проверкой прав и отзывом сессий A06.
- **Риск исправления:** высокий для механизма подтверждения личности; добавление слабого вопроса само по себе не решает задачу безопасности.
- **Проверка:** создать синтетического пользователя через настоящий API, пройти полный согласованный цикл восстановления; подмена пользователя/повтор/истечение подтверждения должны отклоняться. В текущем аудите SQL не выполнялся.

#### A38. Возврат фокуса окна уничтожает открытые формы

- **Приоритет / статус:** средний; регрессия второго этапа, подтверждённая цепочкой исходников и diff коммита `a1eae2d`. Браузерное воспроизведение не выполнено.
- **Место:** `frontend/src/pages/AuthContext.tsx:49`, `:82`; `frontend/src/pages/AuthRedirect.tsx:6`; локальные состояния форм страниц.
- **Проблема и последствия:** при прежнем токене focus вызывает retrySession, который ставит status=checking. Guard заменяет Outlet индикатором; страница и диалоги размонтируются. После успешного `/protected` они создаются заново, локальные черновики отчёта/задачи/пользователя/команды/отпуска потеряны. Это вывод из кода и правил [сохранения состояния React](https://react.dev/learn/preserving-and-resetting-state), а не результат нового браузерного теста. Повторные чтения страниц дополнительно усиливают N+1.
- **Исправление:** различать первичную проверку/смену пользователя и фоновую перепроверку прежней сессии; сохранять форму при успешной фоновой проверке. При 401/смене пользователя очищать доступ и данные, при изменении роли применять guard. Возможные незавершённые запросы формы учитывать отдельно.
- **Риск исправления:** средний/высокий — нельзя вернуть показ защищённых страниц до первой проверки или смешать данные разных пользователей.
- **Проверка:** заполнить каждый диалог, переключить окно и вернуться при задержанном 200 `/protected`; черновик сохраняется. Дополнительно проверить 401, смену токена/роли и временный 500.

#### A39. Перезагрузка состава команды сбрасывает несохранённые поля

- **Приоритет / статус:** средний; регрессия четвёртого этапа, подтверждена кодом и diff `bd31218`. Браузерное воспроизведение не выполнено.
- **Место:** `frontend/src/pages/Teams.tsx:123`, `:159`, `:202`, `:246`.
- **Проблема и последствия:** один эффект одновременно загружает участников и заново устанавливает teamName/teamDescription/selection. При ошибке загрузки пользователь может изменить текст и нажать «Повторить» — изменение revision сбросит черновик. Поля также доступны во время PUT; введённое после отправки будет затёрто ответом и последующим эффектом. Блокировка кнопки Save не блокирует ввод.
- **Исправление:** отделить инициализацию формы при открытии от обновления состава; на время сохранения блокировать редактирование либо сохранять изменения, сделанные после отправки. Retry загрузки участников не должен сбрасывать текст.
- **Риск исправления:** низкий/средний — сохранить очистку selection после подтверждённого успеха и актуальность состава A14.
- **Проверка:** ошибка GET → редактирование → retry; задержанный PUT → попытка ввода; успешное/неуспешное сохранение и повторное открытие. Согласованный черновик должен сохраняться без повторного добавления участников.

### A01. Нет серверной аутентификации, ролей и проверки владельца

- **Приоритет / статус:** критический; исправлено и проверено во втором согласованном этапе 12 ноября 2026 года. Полный жизненный цикл сессии остаётся в A06.
- **Место:** backend/middleware/authMiddleware.js, все backend/routes/*Routes.js, backend/models/authModel.js, backend/controllers/authController.js, backend/controllers/reportController.js, backend/models/reportModel.js; frontend/src/lib/api.ts, AuthContext.tsx, AuthRedirect.tsx, App.tsx и страницы с API-вызовами.
- **Проблема и последствия до исправления:** анонимный клиент мог читать и изменять бизнес-данные, создавать пользователей с выбранной ролью и отправлять отчёт от чужого имени. JWT выдавался, но не защищал бизнес-маршруты. Внешняя доступность рабочего API не проверялась.

Менеджер управляет всеми командами/сотрудниками/задачами/отпусками и принимает отчёты; работник читает только свои задачи/команду/отпуск. Обе роли отправляют отчёт только по собственной задаче, автор берётся из req.user. Создание пользователя защищено ролью менеджера. Вход и восстановление остаются публичными. Frontend передаёт JWT общим клиентом и проверяет сессию до показа защищённых страниц.
- **Риск и ограничения:** внешним клиентам теперь нужен Bearer-заголовок; backend/frontend обновляются согласованно. На запрос добавляется чтение пользователя из БД. Схема не содержит отдельного признака активности: проверяется существование пользователя и разрешённая роль. A03, оставшаяся A06 и настройка адресации A09 не закрыты.

Проверены чужие данные/задачи, изменение роли в БД при старом JWT, неизвестная роль, удалённый пользователь, ошибки БД и разрешённые действия обеих ролей. ### A02. Произвольный сброс пароля без подтверждения восстановления

- **Приоритет / статус:** критический; исходный обход исправлен и проверен 12 ноября 2026 года. Надёжный канал восстановления остаётся отдельной задачей.
- **Место:** backend/controllers/authController.js, backend/models/authModel.js, backend/utils/passwordRecovery.js, backend/routes/authRoutes.js, frontend/src/pages/LoginPage.tsx; тесты backend/tests/.
- **Проблема и последствия до исправления:** newPass принимал только tg_id и textNewPassword без подтверждения; recAns раскрывал ответ и допускал совпадение null. При доступном API можно было заменить пароль по известному идентификатору. Текущая БД и реальные аккаунты при проверке не использовались.
- **Исправление:** recAns после непустого верного ответа выдаёт случайное 256-битное разрешение на 5 минут. В памяти сохраняется SHA-256 хеш, привязанный к users.id и tg_id; новое разрешение отменяет предыдущее. newPass синхронно расходует разрешение до SQL и обновляет только подтверждённый id. Ввод валидируется; секретный ответ/внутренние ошибки не возвращаются. Все три маршрута имеют общий лимит 15 запросов на аккаунт и 60 на IP за 15 минут. Объём хранилищ ограничен.
- **Риск и ограничения:** один backend-процесс; перезапуск отменяет разрешения и сбрасывает счётчики. После SQL/сетевой ошибки может потребоваться повторное подтверждение. Аккаунты с пустыми вопросом/ответом или дублирующимся tg_id не получают разрешение. Проверочный вопрос остаётся слабым подтверждением личности, ранее раскрытые ответы не обезврежены. Пароли пока открытые (A03), старые JWT не отзываются (A06).
- **Проверка:** пройдены модульные и HTTP-проверки прямого обхода, неверного/null-ответа, подмены пользователя, TTL, повторного/параллельного запроса, SQL-ошибки, дубля tg_id и лимитов. ### A03. Пароли сохраняются и сравниваются без хеширования

- **Приоритет / статус:** исходно высокий; код исправлен третьим этапом. Восьмым этапом read-only проверены все 10 текущих записей: поддерживаемый формат scrypt, legacy/unusable — 0, legacy-вход выключен. Исходный дефект хранения открытых password не актуален для этого снимка; повторное преобразование не выполнялось. Происхождение/время предыдущего перехода и вход каждого аккаунта не проверялись. A05 остаётся отдельной проблемой.
- **Место:** backend/utils/passwords.js, backend/controllers/authController.js, backend/models/authModel.js, backend/scripts/migrate-passwords.js, frontend/src/pages/LoginPage.tsx и users.tsx; новые password/migration tests.
- **Проблема и последствия до исправления:** создание и reset сохраняли открытый пароль, login сравнивал его через ===; утечка БД/дампа раскрывала исходное значение. Bcrypt был установлен, но не применялся.
- **Исправление:** встроенный crypto.scrypt (N=32768,r=8,p=3), случайная соль 16 байт, версия/параметры/соль/ключ в password text. Новых требований длины нет; пароль целиком обрабатывается в UTF-8 без обрезания или нормализации. У reset снят прежний лимит 1024 символа, лимит JSON сохранён. Сравнение ключей timingSafeEqual. Legacy-вход разрешён только до явного LEGACY_PASSWORD_LOGIN_UNTIL; правильный пароль заменяется хешем условным UPDATE. При конфликте проверяется текущий хеш до JWT. Подготовлен скрипт с READ ONLY dry-run по умолчанию, явным target/--apply, условным обновлением и безопасными счётчиками.
- **Риск и ограничения:** перед рабочим запуском обязателен согласованный переход записей или временное окно, иначе старые аккаунты не войдут. Внешний потребитель users.password может быть несовместим. Форматы с признаками повреждённого/неподдерживаемого хеша не превращаются в plaintext fallback и требуют отдельного разбора. Хеширование не обезвреживает уже раскрытый пароль (A05), не отзывает JWT (A06). Работающая БД и .env в этапе не менялись.
- **Проверка:** длинные Unicode-пароли и пробелы, различия за 72 байтами, отсутствие нормализации, hash-as-password, неверные форматы, временный переход/истечение срока, параллельные входы/reset, создание/reset/API без секретов, dry-run/идемпотентность/полнота обхода и CLI проверены на синтетических БД. Пройдены 66 backend-тестов, 9 frontend-тестов и 12 браузерных сценариев; детали ниже.

### A25. Bootstrap зависит от дампа; нет управляемого изменения схемы

- **Приоритет / статус:** средний; подтверждено репозиторием, сбой восстановления условный.

### Третий согласованный этап — пароли и вход, 12 ноября 2026 года

## Седьмой согласованный этап — отзыв сессий, 15 ноября 2026 года

**Реализация:**

- users.session_version INTEGER NOT NULL DEFAULT 0 и числовой claim sessionVersion. Middleware проверяет версию в прежнем запросе пользователя; нового SQL на каждый бизнес-запрос не добавлено. JWT без версии, с неверным типом/диапазоном или несовпадением отклоняется с 401. В безопасные DTO поле не добавлено.
- Logout условно увеличивает версию по id и версии аутентифицированного запроса. Отзываются все устройства данного пользователя; повторный старый запрос не затрагивает последующий вход. Другие пользователи сохраняют сессии. Сервер не возвращает Set-Cookie при logout, чтобы поздний ответ не стёр новый вход.
- Действующий reset меняет пароль и увеличивает версию одним UPDATE. Ошибка SQL откатывает обе части. Login подписывает версию, прочитанную вместе с проверяемым паролем; параллельный reset не позволяет получить пригодный JWT по старому паролю.

Успех сообщает о завершении всех сессий, 401 — о недействительной текущей сессии; сетевой/серверный отказ предупреждает, что серверный отзыв не подтверждён. Автоматический 401 выполняет локальную очистку без рекурсивного logout. Поздний ответ не удаляет новый token.
