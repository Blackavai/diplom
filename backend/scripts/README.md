# Административные скрипты

Текущий парольный цикл и новая миграция рекомендации описаны в разделе «Этап 15» ниже.
Указания первых этапов о непроверенных рабочих password сохраняют исторический контекст;
формат scrypt рабочих записей был подтверждён этапом 8. Рабочее применение новых скриптов отдельно.

## Переход паролей на scrypt — история и процедура для legacy-сред

Этот раздел описывает пароли. Добавление поля отзыва сессий описано отдельно в конце файла и само по себе не преобразует password.

Схема БД не меняется: код хранит в прежнем `users.password` строку
`scrypt$1$32768$8$3$<соль-hex>$<ключ-hex>`. Используются N=32768, r=8, p=3,
случайная соль 16 байт, ключ 64 байта; пароль целиком кодируется UTF-8.
Пробелы и Unicode не нормализуются, длина пароля не обрезается. Новых требований
к длине нет; HTTP сохраняет существующий лимит `express.json()`.

Параметры взяты из [рекомендаций OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt).
Встроенный [crypto.scrypt Node 20](https://nodejs.org/docs/latest-v20.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)
не требует новой зависимости. На процесс допускаются 2 активных вычисления и
16 ожидающих; предел памяти одного вызова — 64 МиБ. Переполнение очереди даёт
503, `Retry-After: 1`.

## Включение новой версии

Рабочая БД в третьем этапе **не преобразовывалась**. Перед обновлением рабочего
backend необходимо выбрать и согласовать переход:

1. Подготовить проверенную резервную копию и сверить внешних потребителей
   `users.password`. Старый backend с прямым сравнением не сможет читать хеши.
2. Либо заранее преобразовать записи согласованной процедурой, либо включить
   временный вход по старым паролям переменной `LEGACY_PASSWORD_LOGIN_UNTIL`.
   Её значение — конкретная будущая дата ISO 8601 с явным часовым поясом,
   например формата `YYYY-MM-DDTHH:mm:ssZ`. Дату выбирает владелец среды.
   Без переменной, при неверной или истёкшей дате старый открытый пароль
   **не принимается**. Перезапуск не продлевает срок.
3. При временном входе правильный пароль заменяется scrypt-хешем через условный
   UPDATE по id и прежнему значению. Неверный пароль не меняет запись.
   Если запись изменилась параллельно, проверяется актуальный хеш до выдачи JWT;
   сброс пароля не перезаписывается старым значением.
4. Завершить преобразование оставшихся записей, отдельно разобрать `unusable`
   и убрать переменную совместимости. Только после этого A03 можно считать
   закрытой для всех рабочих записей. Срок перехода в текущем `.env` не задан
   и самим кодом автоматически не включается.

Существующая схема Compose уже передаёт backend корневой `.env` через env_file.
В этом этапе `.env` и production Compose не менялись. Добавление срока/запуск
преобразования в рабочей среде требуют отдельного согласования.

## Скрипт

```sh
node scripts/migrate-passwords.js --help
node scripts/migrate-passwords.js --database=<ожидаемое-имя-БД>
node scripts/migrate-passwords.js --apply --database=<ожидаемое-имя-БД>
```

Команды выше выполняются из `backend`; подключение использует `db.js` и DB_*
окружения. Не запускайте их с рабочими реквизитами без согласования.
Без `--apply` это `dry-run` в транзакции `READ ONLY`. До чтения записей скрипт
проверяет `current_database()` против явно заданного имени. Вывод — только JSON
со счётчиками, без id, логинов, паролей, хешей и реквизитов подключения.

`--apply` читает по 100 записей, пропускает уже закодированные пароли и меняет
каждую старую запись условным UPDATE. Общей транзакции на всю таблицу нет:
после прерывания уже преобразованные строки сохраняются, повторный запуск их
не хеширует повторно. Конкурентный reset не затирается и учитывается как
`conflicts`. Отрицательные/нулевые id не пропускаются. Схема и другие поля
не меняются; строки пользователей не удаляются.

`unusable` — NULL/пустые значения, повреждённый формат scrypt или иной
распознаваемый формат хеша (например bcrypt). Они требуют отдельного разбора
без вывода содержимого и не превращаются в plaintext fallback. Историческое
значение, похожее на кодированный формат, также требует проверки происхождения.
Штатный скрипт такие значения не перезаписывает.

Хеширование не отменяет ранее раскрытый пароль (A05), не отзывает JWT (A06)
и не усиливает проверочный вопрос восстановления (A02).

## Версия сессий: отдельная миграция схемы

Для backend седьмого этапа нужно поле `public.users.session_version INTEGER NOT NULL DEFAULT 0`.
В историческом дампе этого поля не было; безопасный bootstrap этапа 13 уже содержит
его. Для существующей среды без поля перед первым запуском новой версии нужна миграция.
Повторно загружать дамп, очищать БД или пересоздавать volume не требуется.

Из каталога backend, с DB_* явно выбранной среды:

```sh
node scripts/migrate-sessions.js --help
node scripts/migrate-sessions.js --dry-run --database=<ожидаемое-имя-БД>
node scripts/migrate-sessions.js --apply --database=<ожидаемое-имя-БД>
```

По умолчанию скрипт работает в READ ONLY. `--apply` требует точного совпадения
current_database() с указанным именем и добавляет только поле версии в транзакции.
Уже существующее совместимое поле сохраняется вместе с его значениями;
несовместимая схема или отрицательные версии дают отказ без автоматического ремонта.
Есть lock_timeout 5 секунд и statement_timeout 30 секунд; apply кратко берёт
ACCESS EXCLUSIVE блокировку users. Вывод содержит только mode/status, без данных
пользователей, токенов и реквизитов. Ошибка откатывает изменение.

Рабочее применение требует согласования, резервной копии и проверки восстановления.
15 ноября 2026 года это выполнено для существующей рабочей БД; описание и путь
копии — в седьмом этапе docs/AUDIT.md. Для других сред порядок тот же.

Сначала миграция схемы, затем согласованное совместное обновление API/UI. JWT без
sessionVersion больше не принимаются новым backend: всем нужен повторный вход.
Выход отзывает все устройства пользователя; существующий reset увеличивает версию
одновременно с изменением пароля. Уже начатые операции не отменяются. При отказе
сервера frontend завершает локальный вход, но предупреждает о неподтверждённом отзыве.
Проверки перехода password A03 остаются отдельным условием рабочего включения.

## Этап 13: безопасная первая инициализация и целостность

`itk_old.sql` теперь содержит только схему и две роли приложения. Пользователей,
паролей, ответов восстановления и персональных данных в нём нет. Он по-прежнему
выполняется PostgreSQL только для нового пустого каталога данных. Существующую БД
этим файлом не обновлять и не переинициализировать. Старые копии/коммиты дампа
не очищались; реальные резервные копии хранить отдельно от Git. Папки `backups/`
и `private-backups/` игнорируются, но игнорирование не защищает уже опубликованные
данные. Ранее раскрытые действующие реквизиты требуют отдельного решения о смене.

В новой схеме уже есть `session_version`, ограничения целостности и таблица
`request_idempotency`. Первого менеджера создают явно; стандартного аккаунта нет:

```sh
node scripts/create-manager.js --dry-run --database=<name> --login=<login> --first-name=<name> --last-name=<name> --post=<position>
node scripts/create-manager.js --apply --database=<name> --login=<login> --first-name=<name> --last-name=<name> --post=<position>
```

Режим по умолчанию — read-only. При `--apply` пароль дважды вводится в терминале
без отображения; передавать его аргументом командной строки не нужно. Сохраняется
scrypt-хеш. Скрипт откажет при уже существующем менеджере или занятом логине.
Это создание первого аккаунта, а не будущий административный сброс пароля.

Для существующей схемы подготовлена отдельная недеструктивная миграция:

```sh
node scripts/migrate-integrity.js --dry-run --database=<name>
node scripts/migrate-integrity.js --apply --database=<name>
```

Она проверяет целевую БД, дубли `users.tg_id`, дубли пар `teams(id_team_name,id_user)`
и отсутствующих авторов отчётов. При нарушениях возвращается `blocked-by-data`
с количеством проблем, без личных данных; apply ничего не изменяет и завершается
с ненулевым кодом. Автоматического удаления, объединения или исправления записей нет.
При совместимых данных одна транзакция добавляет UNIQUE, FK автора и таблицу ключей
повторов. При несовместимом одноимённом объекте все изменения откатываются.
Повторный запуск совместим с уже применённой схемой. Порядок дат не меняется.
Есть ограничения ожидания блокировок и времени запросов; применять только после
согласования, актуальной резервной копии и проверки восстановления.

Для нового браузерного API таблица `request_idempotency` должна существовать
до включения новой версии. Сначала подготовка/проверка схемы, затем совместное
обновление backend/frontend. Рабочее применение этапа 13 не выполнялось.

## Этап 13: отдельная runtime-роль

```sh
node scripts/setup-runtime-role.js --dry-run --database=<name> --role=dailysync_app
node scripts/setup-runtime-role.js --apply --database=<name> --role=dailysync_app
```

Скрипты настройки и миграции схемы используют административные `DB_*`, игнорируя
`APP_DB_USER`. Проверка выводит только mode/status и флаги полномочий текущего
подключения, без реквизитов. Новый пароль роли вводится дважды без отображения
и должен иметь не меньше 16 символов. Пароль существующей роли не меняется.

Runtime-роли выдаются CONNECT, USAGE схемы, SELECT справочника ролей, необходимые
SELECT/INSERT/UPDATE/DELETE таблиц API и USAGE/SELECT соответствующих sequence.
Не выдаются права управления ролями/БД/постоянной схемой, права владельца, TRUNCATE
или передача прав. Существующая роль с избыточными флагами, членством, владением
или лишними эффективными правами отклоняется; чужие права автоматически не отзываются.
`daily_reports` не используется API и runtime-роли не предоставляется.

После отдельного согласования подключения:

- `DB_USER/DB_PASSWORD` сохраняются для bootstrap и административных скриптов;
- `APP_DB_USER/APP_DB_PASSWORD` задаются отдельной парой для API;
- если APP_DB_USER указан без APP_DB_PASSWORD, API отказывается запускаться;
- Compose передаёт API выбранные runtime-реквизиты; порты и сеть не меняются.

При npm-запуске `backend/.env` приложения должен содержать только runtime-реквизиты
в DB_USER/DB_PASSWORD. Административные DB_* для скриптов задаются отдельному процессу
из приватного env-файла (например, `node --env-file=/private/path/admin.env ...`),
без передачи административного пароля работающему API.

Без APP_DB_USER прежнее подключение сохраняется. Рабочий `.env`, права и контейнеры
не переключались. Это не подтверждает ограниченность текущей рабочей роли.

## Этап 13: браузерная сессия и повторы

Браузерный POST `/api/auth/login` отправляет `X-Requested-With: XMLHttpRequest`.
Ответ устанавливает `dailysync_session` с HttpOnly, SameSite=Lax, Path=/api и сроком
один час; JWT в JSON отсутствует. `SESSION_COOKIE_SECURE=true` включают только
для реально настроенного HTTPS. Для локального HTTP используется false; TLS не добавлен.

GET `/api/auth/protected` возвращает безопасного пользователя, `sessionId` и
`csrfToken`. Cookie-запросы изменения, включая старый GET удаления, требуют
`X-Session-Id` и `X-CSRF-Token`. CSRF привязан к конкретному JWT; proof старого
входа не применяется к новому. Явный небраузерный login с `X-Auth-Mode: bearer`
сохраняет выдачу `user.token`, не устанавливает cookie и отклоняется при Origin
или Sec-Fetch-Site. Автоматизированным клиентам нужно явно выбрать этот режим.

Выход отзывает прежние сессии в БД. Сервер не отправляет очистку cookie, чтобы
поздний ответ не перезаписал новый вход. Оставшаяся HttpOnly-cookie уже недействительна
и истекает сама. При неудавшемся отзыве UI сохраняет локальный признак выхода и
предупреждает, что серверный отзыв не подтверждён. localStorage содержит только
уведомления вкладкам, без JWT или CSRF; права всегда подтверждает backend.

Создание команды и отчёта из браузера требует UUID в `Idempotency-Key`. Повтор
того же ключа с теми же данными возвращает прежний результат; изменение данных —
409. Ключи ограничены пользователем и видом операции, результат сохраняется в одной
транзакции с действием и переживает перезапуск backend. Срок автоматического
удаления ключей не введён. Для прежних Bearer-клиентов ключ необязателен; без него
создание команды не гарантирует устранение повторов.

Новый отчёт допустим только по собственной незавершённой задаче. Другой запрос
по завершённой задаче — 409. Менеджер может открыть задачу существующим PUT;
следующий отчёт сохраняется отдельно, предыдущие не удаляются. Повтор старого ключа
возвращает старый результат и не завершает вновь открытую задачу.

## Этап 14, пункт 2: диапазоны календарных дат

Новый bootstrap содержит CHECK начала/окончания задач и отпусков. Для существующих
схем подготовлен отдельный скрипт; рабочее применение не выполнялось:

```sh
node scripts/migrate-date-ranges.js --dry-run --database=<name>
node scripts/migrate-date-ranges.js --apply --database=<name>
```

По умолчанию транзакция read-only. Несовпадение имени БД отклоняется. Неверные
исторические диапазоны дают `blocked-by-data` и только количества проблем;
строки автоматически не изменяются. Применение добавляет оба CHECK одной
транзакцией, несовместимое существующее ограничение приводит к откату.
Повторное применение совместимых ограничений безопасно. Перед рабочим apply
нужны отдельное согласование, резервная копия и проверка восстановления.

API принимает YYYY-MM-DD и прежние ISO timestamp, сохраняет их календарную часть.
Ответы PostgreSQL DATE возвращаются строкой YYYY-MM-DD; TIMESTAMP не меняется.
Начало должно быть не позже окончания; текущий день и последний включительный
день отпуска определяются по Europe/Moscow. Это изменение контракта ответов:
backend/frontend должны включаться совместно. Исторические даты не пересчитываются.

## Этап 15: рекомендация смены пароля и сброс менеджером

Этот раздел описывает текущий парольный цикл и заменяет старое восстановление по
вопросу. Начальный пароль не имеет срока; доступ после входа не ограничивается.
Менеджер вводит пароль при создании/сбросе и передаёт его лично. API не возвращает
пароли. Журнала смен/сбросов и дополнительной таблицы нет.

Добавляется одно поле users.password_change_recommended BOOLEAN NOT NULL DEFAULT false.
Миграция сохраняет password, role, session_version, question/answer и остальные данные:

```sh
node scripts/migrate-password-lifecycle.js --dry-run --database=<expected-database>
node scripts/migrate-password-lifecycle.js --apply --database=<expected-database>
```

По умолчанию — read-only, имя БД обязательно. Apply добавляет только поле в транзакции,
с ограниченным ожиданием блокировки/запросов. Несовместимое существующее поле даёт отказ
без ремонта; повторный запуск сохраняет текущие true/false. Значение false оставляет
существующие аккаунты без новой рекомендации. Новые createUser/create-manager явно
задают true. Runtime-роли достаточно прежних прав на users; новых таблиц/прав нет.
Рабочее применение этим этапом не выполняется: сначала согласованные backup/restore,
dry-run и миграция, затем совместное обновление API/UI. Не загружать bootstrap в
существующую БД и не пересоздавать volume.

POST /api/auth/change-password принимает currentPassword,newPassword,confirmPassword.
Пользователь определяется по сессии. Новый пароль должен отличаться от текущего;
после смены рекомендация снимается и прежние сессии отзываются, нужен повторный вход.
POST /api/auth/users/:id/reset-password принимает те же поля, currentPassword — пароль
менеджера. Только менеджер и только другой пользователь (работник или менеджер).
Сброс включает рекомендацию и отзывает сессии адресата, сохраняя сессию менеджера.
Cookie-запросы требуют существующие X-Session-Id/X-CSRF-Token. Неподтверждённый сетевой
результат не повторяется автоматически: сначала проверить доступ с новым паролем.
Проверки попыток — 10/user и 60/IP за 15 минут в памяти одного процесса.

Старые POST /recPass, /recAns, /recPass/newPass под /api/auth возвращают 410/no-store
и не выдают разрешения/не меняют пароль. Старые question/answer остаются в БД.
Внешние клиенты этих маршрутов должны перейти к восстановлению через менеджера.

### Если потерян доступ менеджера, включая последнего

Владелец среды использует административное окружение DB_* отдельно от runtime API.
Право выполнения определяется доступом владельца к этому окружению; публичного API
или стандартного пароля для обхода нет. Сначала проверить целевую БД и id менеджера:

```sh
node scripts/reset-manager-password.js --dry-run --database=<expected-database> --user-id=<manager-id>
node scripts/reset-manager-password.js --apply --database=<expected-database> --user-id=<manager-id>
```

Apply требует скрытый ввод нового пароля дважды; аргументы --password не принимаются.
Скрипт проверяет роль 1, меняет пароль на scrypt, включает рекомендацию и увеличивает
session_version атомарно. Конкурентное изменение реквизитов даёт отказ, остальные
пользователи/роли/question/answer не меняются. Вывод — mode/status без секретов.
Применение к рабочему менеджеру — отдельная явная операция владельца среды.
