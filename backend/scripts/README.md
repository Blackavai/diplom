# Переход паролей на scrypt

Схема БД не меняется: код хранит в прежнем `users.password` строку
`scrypt$1$32768$8$3$<соль-hex>$<ключ-hex>`. Используются N=32768, r=8, p=3,
случайная соль 16 байт, ключ 64 байта; пароль целиком кодируется UTF-8.
Пробелы и Unicode не нормализуются, длина пароля не обрезается. Новых требований
к длине нет; HTTP сохраняет существующий лимит `express.json()`.

Параметры взяты из [рекомендаций OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt).
Встроенный [crypto.scrypt Node 20](https://nodejs.org/docs/latest-v20.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)
не требует новой зависимости. На процесс допускаются 2 активных вычисления и
16 ожидающих; предел памяти одного вызова — 64 МиБ. Переполнение очереди даёт
503, `Retry-After: 1`.

## Включение новой версии

Рабочая БД в третьем этапе **не преобразовывалась**. Перед обновлением рабочего
backend необходимо выбрать и согласовать переход:

1. Подготовить проверенную резервную копию и сверить внешних потребителей
   `users.password`. Старый backend с прямым сравнением не сможет читать хеши.
2. Либо заранее преобразовать записи согласованной процедурой, либо включить
   временный вход по старым паролям переменной `LEGACY_PASSWORD_LOGIN_UNTIL`.
   Её значение — конкретная будущая дата ISO 8601 с явным часовым поясом,
   например формата `YYYY-MM-DDTHH:mm:ssZ`. Дату выбирает владелец среды.
   Без переменной, при неверной или истёкшей дате старый открытый пароль
   **не принимается**. Перезапуск не продлевает срок.
3. При временном входе правильный пароль заменяется scrypt-хешем через условный
   UPDATE по id и прежнему значению. Неверный пароль не меняет запись.
   Если запись изменилась параллельно, проверяется актуальный хеш до выдачи JWT;
   сброс пароля не перезаписывается старым значением.
4. Завершить преобразование оставшихся записей, отдельно разобрать `unusable`
   и убрать переменную совместимости. Только после этого A03 можно считать
   закрытой для всех рабочих записей. Срок перехода в текущем `.env` не задан
   и самим кодом автоматически не включается.

Существующая схема Compose уже передаёт backend корневой `.env` через env_file.
В этом этапе `.env` и production Compose не менялись. Добавление срока/запуск
преобразования в рабочей среде требуют отдельного согласования.

## Скрипт

```sh
node scripts/migrate-passwords.js --help
node scripts/migrate-passwords.js --database=<ожидаемое-имя-БД>
node scripts/migrate-passwords.js --apply --database=<ожидаемое-имя-БД>
```

Команды выше выполняются из `backend`; подключение использует `db.js` и DB_*
окружения. Не запускайте их с рабочими реквизитами без согласования.
Без `--apply` это `dry-run` в транзакции `READ ONLY`. До чтения записей скрипт
проверяет `current_database()` против явно заданного имени. Вывод — только JSON
со счётчиками, без id, логинов, паролей, хешей и реквизитов подключения.

`--apply` читает по 100 записей, пропускает уже закодированные пароли и меняет
каждую старую запись условным UPDATE. Общей транзакции на всю таблицу нет:
после прерывания уже преобразованные строки сохраняются, повторный запуск их
не хеширует повторно. Конкурентный reset не затирается и учитывается как
`conflicts`. Отрицательные/нулевые id не пропускаются. Схема и другие поля
не меняются; строки пользователей не удаляются.

`unusable` — NULL/пустые значения, повреждённый формат scrypt или иной
распознаваемый формат хеша (например bcrypt). Они требуют отдельного разбора
без вывода содержимого и не превращаются в plaintext fallback. Историческое
значение, похожее на кодированный формат, также требует проверки происхождения.
Штатный скрипт такие значения не перезаписывает.

Хеширование не отменяет ранее раскрытый пароль (A05), не отзывает JWT (A06)
и не усиливает проверочный вопрос восстановления (A02).

## Проверка

`backend/tests/migratePasswords.integration.test.js` создаёт отдельную БД
`dailysync_password_migration_test` только внутри синтетического PostgreSQL
тестового Compose. Проверяются dry-run, явный target, преобразование длинных
паролей, повторный запуск, конкурентный reset, полнота обхода и безопасный CLI.
К текущей БД эти проверки не подключаются. Общий запуск описан в
`backend/tests/README.md`, результаты — в `docs/AUDIT.md`.
