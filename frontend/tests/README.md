# Проверки авторизации frontend

Новые зависимости не нужны: Node test runner, React, Axios и esbuild уже доступны
в существующем образе сборки frontend. Команды Docker выполняются из корня проекта.

## Клиент и guard

```sh
docker compose --env-file /dev/null -f docker-compose.recovery-test.yml -p itrum-access-check build frontend-checks
docker compose --env-file /dev/null -f docker-compose.recovery-test.yml -p itrum-access-check run --rm --no-deps frontend-checks node --test tests/access.test.mjs
docker compose --env-file /dev/null -f docker-compose.recovery-test.yml -p itrum-access-check down
```

14 тестов проверяют cookie/CSRF/sessionId, публичные запросы без JWT, 401/403,
поздний ответ старой сессии, безопасные логи, ожидание проверки и доступ по роли.
Axios adapter и cookie/toast заменены тестовыми объектами; запросов к API нет.
Guard проверяется React SSR; переходы и эффекты дополнительно проверяются в браузере.
Дополнительно проверяются запрет отправки до подтверждения сессии, сброс разрешения
на отправку, недопустимый ручной Bearer в браузерном клиенте и сохранение проверенной страницы при
фоновой проверке/временной ошибке. Блокируется и прежний изменяющий GET удаления
сотрудника; чтение и публичные вход/восстановление остаются доступными.
Истечение HttpOnly-cookie обнаруживается сервером: запрос отклоняется с 401,
локальная сессия закрывается, следующих отправок формы нет.

## Vite dev/preview и границы доступа

После сборки `frontend-checks` по инструкции выше:

```sh
docker run --rm --network none itrum-access-check-frontend-checks node --test tests/access.test.mjs tests/dev-server.test.mjs
```

Нужен Node 24 LTS; новые библиотеки не используются. Совместный запуск после
шестого этапа содержит 21 проверку (14 клиента/guard, 6 подсценариев Vite и общий сценарий).
`dev-server.test.mjs` поднимает настоящий Vite dev/preview с текущей конфигурацией,
временной синтетической SPA и искусственным API только на loopback. Проверяет:
bind `127.0.0.1`, возможность явного container host, отклонение постороннего Host,
SPA deep links, proxy `/api/` и `/api-docs/`, Bearer/cookie и статусы
200/401/403/404/429 с Retry-After, HMR WebSocket и обновление модуля.

Тесты доступа к файлам используют только созданные ими текст/HTML вне корня
временной SPA. Проверяется блокировка прямого доступа, HTML traversal и безвредной
попытки добавить искусственный файл через virtual module из advisory Vite.
Команды и payload выполнения кода не применяются. Временные файлы удаляются
после теста. Существующий backend/БД, рабочий `.env` и Docker volumes не используются.

## Собранный интерфейс в headless Chrome

Нужны локальные Chrome и Node >=22 (в проверке использовался Node 24). Используйте
только отдельный временный профиль Chrome, без личных cookie и открытых вкладок.
Выбранные имена контейнеров/проекта должны быть свободны.

После сборки образа выше можно раздать статику через существующий Vite preview:

```sh
docker run -d --name itrum-access-browser -p 127.0.0.1::5173 itrum-access-check-frontend-checks npm run preview -- --host 0.0.0.0 --port 5173
docker port itrum-access-browser 5173
```

Запустите отдельный Chrome с `--headless=new --no-first-run`,
`--disable-background-networking --disable-component-update --disable-sync`,
`--remote-debugging-port=0` и `--user-data-dir=<новый временный каталог>`.
Из строки `DevTools listening on ws://127.0.0.1:PORT/...` возьмите порт CDP.
Из `docker port` возьмите порт статики и выполните на хосте:

```sh
node frontend/tests/browser-access.mjs <порт-CDP> http://127.0.0.1:<порт-статики> --close-browser
```

Скрипт перехватывает **все** обращения к текущему адресу API до сети, поэтому
рабочий backend не вызывается. Внешние HTTPS-ресурсы блокируются. Cookie, ответы,
пользователи и токены искусственные. Проверяются 45 сценариев: прежние 17
(12 авторизации/паролей и пять команд), 16 регрессионных сценариев шестого этапа
пять сценариев серверного выхода седьмого этапа и семь сценариев сотрудников девятого этапа.
Исходные проверки включают анонимный переход,
ожидание сервера и подмена роли cookie, свои задачи/повреждённый кэш, 401 при
бизнес-запросе, временная ошибка/retry, доступ менеджера, повторный вход с тем же
токеном, 403 без logout и просроченная сессия при загрузке. Добавлены длинные
пароли во входе/сбросе/создании пользователя, блокировка двойной отправки и
отображение 429. Значения сверяются с исходными без печати паролей в результатах.
Флаг `--close-browser` закрывает только выделенный тестовый экземпляр Chrome
через CDP; используйте его исключительно с отдельным временным профилем.

Новые сценарии воспроизводят focus с задержанным ответом, 500/retry и запрет
отправки до успешного ответа, черновики сотрудников/отчётов/задач/отпусков/команд,
истечение cookie во время ввода, понижение роли, фоновые 401/403, смену пользователя и поздние 200/401 прежнего
токена, выход с незавершённой проверкой. Для команд проверяются retry состава
без потери полей/selection, блокировка ввода при сохранении, сохранность после
ошибки и повторное открытие после успеха. Кнопка повтора проверки сессии внутри
диалога проверяется настоящим нажатием мыши через CDP, а не только вызовом onClick.
Флаги `--only-session-regression` и `--only-team-regression` нужны для раздельного
воспроизведения исходных A38/A39; полную приёмку выполнять без этих флагов.

Седьмой этап проверяет POST logout с явно переданным Bearer, результаты 200/401/500,
немедленную локальную очистку и сообщение о неподтверждённом отзыве при отказе,
сохранность более нового входа при позднем ответе и отсутствие повторного серверного
logout из обработчика 401. Запрос выхода имеет timeout 15 секунд и доступен при
ошибке проверки сессии. Реальное изменение версии в БД проверяется backend-тестами.

Девятый этап: неверные/неполные поля не вызывают POST, поля и роль заблокированы
при сохранении, 409/500 сохраняют форму, успех показывает сотрудника и сбрасывает
видимый выбор роли. Отдельно проверены поздний GET до создания, отказ reload с retry
без повторного POST и поздний ответ, возвращавший уже удалённую запись.
Роль выбирается настоящим нажатием мыши через CDP: прежний искусственный pointerup
фактически не выбирал её. При сбое выводятся только длины полей и пути/коды API,
без паролей и Bearer. В реальном browser-proxy перед отправкой ожидается окончание
фоновой проверки сессии; общий запрет записи до подтверждения не ослаблялся.

Первая проверка — функциональная проверка React с искусственными ответами, не сквозной тест
браузер → рабочий backend/БД. Backend/CORS/транзакции отдельно проверяются
`backend/tests/access.integration.test.js`. Внешний доступ, TLS, proxy и все
визуальные состояния этим скриптом не подтверждаются; проверка реального proxy описана ниже.

Если флаг закрытия не использовался, завершите запущенный тестовый Chrome.
Затем уберите свой контейнер:

```sh
docker stop itrum-access-browser
docker rm itrum-access-browser
```

Volumes для браузерного контейнера не создаются. Результаты фактического запуска
согласованных этапов записаны в `docs/AUDIT.md`.

## Четвёртый этап

Оба Axios-клиента используют относительный `/api`. Браузерный перехват теперь
охватывает `<origin frontend>/api/*`; старый localhost:5001 не используется.
17 сценариев включают прежние 12 и пять проверок команд: один запрос создания,
блокировку двойной отправки, исключение существующих участников, обновление
состава/очистку выбора, повторное открытие, ошибку загрузки/retry и сохранение
черновика после ошибки создания. Условие ожидания сохранения проверяет доступность
кнопки после повторной загрузки состава, а не только количество строк.

### Реальная цепочка браузер → proxy → backend → тестовая БД

Запустите отдельный профиль `proxy` по инструкции
[backend/tests/README.md](../../backend/tests/README.md). Создайте только тестовую
учётную запись и определите временный порт Nginx:

```sh
docker compose --env-file /dev/null -f docker-compose.recovery-test.yml -p itrum-proxy-check exec -T proxy-app node tests/proxy-smoke.js --seed-browser
docker compose --env-file /dev/null -f docker-compose.recovery-test.yml -p itrum-proxy-check port proxy-nginx 80
```

С отдельным Chrome, запущенным по инструкции выше, выполните:

```sh
node frontend/tests/browser-proxy.mjs <порт-CDP> http://127.0.0.1:<порт-Nginx> browser-proxy-manager
```

Этот скрипт **не перехватывает API**: проверяет настоящий вход через форму,
проверку сессии, создание сотрудника/появление в списке/сброс роли/удаление тестовой записи,
создание/удаление синтетической команды, отправку отчёта с исчезновением задачи,
выход/отказ старому JWT и то, что все запросы
`/api` идут к origin frontend. Допускает только loopback URL и фиксированные
синтетические имена пользователей. Он предназначен исключительно для тестовой
среды; не направляйте его на рабочий frontend. Пароль синтетической записи
задан в тесте. Стандартные browser-access тесты выполняйте отдельным запуском.

Для двух npm-процессов аналогично проверяется loopback-адрес Vite с отдельно
подготовленной синтетической БД и пользователем `host-proxy-manager`. В четвёртом
этапе это действительно выполнено на компьютере во временной копии репозитория,
с `npm ci` из lock-файлов, Node 24.20.0 и PostgreSQL 17 в отдельном Docker-проекте.
Порты frontend/backend/БД были случайными и отличались от стандартных. Рабочий
`.env`, существующий node_modules и рабочая БД не использовались.

По окончании закройте выделенный Chrome (или используйте поддержанный
browser-access.mjs флаг `--close-browser`), остановите свои npm-процессы и
удалите только контейнеры/сеть своего тестового проекта без `-v`.

## Десятый этап: отчёт и собственные задачи

С отдельным Chrome и тестовым frontend по инструкции выше:

```sh
node frontend/tests/browser-reports.mjs <порт-CDP> http://127.0.0.1:<порт-frontend> --close-browser
```

Все API-запросы перехватываются до сети; рабочая БД не используется.
13 сценариев проверяют загрузку/error/empty и retry, валидацию текста,
двойное нажатие и блокировку ввода, сохранность черновика при 400/500,
немедленное исчезновение завершённой задачи, поздний GET и отказ перечитывания,
настоящие 15-секундные timeout GET/POST, сетевой отказ, сверку неопределённого
результата без автоматического POST и поздние ответы после смены пользователя.
Два timeout делают запуск длиннее 30 секунд. Прежние 45 сценариев
browser-access.mjs остаются отдельным регрессионным набором.

Для реального browser-proxy.mjs сначала выполните --seed-browser по инструкции
backend/tests/README.md. Синтетическому browser-proxy-manager добавляется
«Browser proxy report task». Браузер отправляет отчёт двойным нажатием,
проверяет единственный POST и исчезновение задачи без reload. Перед проверкой
другого proxy повторите --seed-browser, чтобы подготовить новую незавершённую
задачу. Для своей host-fixture требуется такая же собственная задача.


## Этап 13

Клиент/guard/Vite: **21 passed**. JWT не читается из cookie и не добавляется
браузером в Authorization. Проверены withCredentials, CSRF/sessionId на изменениях,
запрет ручного Bearer, блокировка до проверки и игнорирование позднего 401 прежнего
поколения сессии. Обработку ролей/ошибок guard прежние проверки сохраняют.

browser-access.mjs адаптирован к HttpOnly-cookie и безопасному proof: **45 сценариев**,
включая черновики, временные ошибки, уведомление смены пользователя между вкладками,
отзыв и поздний ответ logout. Истечение cookie теперь проверяется отказом сервера,
а не чтением секрета из document.cookie. browser-reports.mjs: **13 сценариев**,
включая настоящие 15-секундные таймауты и одинаковые ключ/payload при повторе после
серверной ошибки. Через тестовые Nginx и Vite проверки прошли.

browser-proxy.mjs проверяет реальную цепочку UI → proxy → Express → PostgreSQL:
вход, сотрудник/команда, отчёт и logout. CDP только своего отдельного профиля
подтверждает HttpOnly/Lax/path; document.cookie не содержит JWT. Старый JWT для
проверки отзыва берётся только тестовым CDP, не кодом приложения и не из реального
аккаунта. Перед каждым proxy-прогоном нужна свежая синтетическая задача через
backend/tests/proxy-smoke.js --seed-browser.

Общие frontend-проверки остаются неуспешными: 5 ошибок/4 предупреждения ESLint,
97 ошибок TypeScript. Сравнение нормализованной диагностики с исходным HEAD
не выявило новых ошибок. Общий долг и вёрстка остаются этапу 14; strict/правила
не отключались, новые библиотеки и CI не вводились.

## Этап 14, только пункты 1–2

```sh
docker compose --env-file /dev/null -f docker-compose.recovery-test.yml -p <test-project> run --rm --no-deps frontend-checks node --test tests/access.test.mjs tests/dev-server.test.mjs tests/dates.test.mjs
```

**22 passed**: прежние проверки и dates.test.mjs для выбора/отображения дня в UTC,
Москве, Лос-Анджелесе и Токио, совместимости ISO и московской полуночи. Ответ DATE
не переводится в UTC, календарный выбор отправляется YYYY-MM-DD. Browser-reports
ожидает календарную дату отчёта; механизм сохранения ключа/черновика не изменён.
Сервер больше не удаляет через GET (405), штатный UI использует прежний DELETE.

Реальные browser-proxy проверки прошли через Nginx и Vite. Общие TS/lint остаются
неуспешными: 91 ошибка TS, 4 ошибки/4 предупреждения lint; новых TS-диагностик
относительно зафиксированного этапа 13 нет. Это не выполнение общих исправлений
типов, форм и вёрстки: пункты 3–5 ожидают команды пользователя.
